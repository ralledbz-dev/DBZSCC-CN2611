# Lokale LangChain-Workflowplanung

Die Workflowplanung verwendet `langchain-core` mit `RunnableParallel`, `RunnableLambda`, einer `RunnableSequence` und `PydanticOutputParser`. Der Planer sendet ausschließlich den ausdrücklich eingegebenen Auftrag an einen Loopback-Endpunkt. Er liest keine Projektdateien und sendet weder Quellcode noch Projektpfade.

Die Modellantwort wird gegen ein striktes Pydantic-Schema mit fester Aktions-Allowlist validiert. Erlaubte Vorschläge sind Projektstatus prüfen, Tests, Linter, Entwicklungsserver, Debug-Session und Patchvorschlag. Die Planung führt keine dieser Aktionen aus. Das Schema verwirft unbekannte Felder und Aktionen; fehlerhafte Antworten werden fail-closed abgelehnt.

Projektprozesse sind inzwischen in separaten, bewusst engen Slices angebunden: feste projektlokale pytest-/Ruff-Argumente sowie manifestgebundene PySide6-Module oder Uvicorn-ASGI-Ziele, jeweils mit validiertem Interpreter/Projektpfad, frischer Ressourcen- und Fingerprintprüfung, Zeit-/Ausgabegrenzen, Cancellation und Windows-Prozessbaumaufsicht. Vor jedem Start verlangt die UI eine eigene Freigabe. Das ist weder eine allgemeine Shell noch eine Sandbox. Patchvorschläge bleiben reviewbare Diffs und werden nie automatisch angewendet.


## Live-Verifikation und Grenzen — 3. November 2026

Der optionale Adapter ist in Python 3.14.4 mit `langchain-core 0.3.86`, `langsmith 0.14.17` und `pydantic 2.14.2` verfügbar. Ein echter Qwen2.5-0.5B-Instruct-CPU-Server wurde vom app-eigenen Runtime-Controller gestartet; der lokale `/health`-Endpunkt wechselte beim Laden von HTTP 503 zu HTTP 200. Danach wurde ein realer lokaler `RunnableSequence`-Auftrag gegen die tatsächliche `/v1/models`-Kennung ausgeführt. Die Antwort bestand die Pydantic-/Allowlist-Prüfung und schlug `inspect_project` sowie `run_tests` vor. Der Auftrag wurde nicht als Aktion ausgeführt und es wurden keine Projektdateien an das Modell gesendet.

`run-dbzscc-2611.ps1` startet die isolierte Python-3.14.4-Umgebung. Die vollständige aktuelle Testsuite lief dort mit **262 passed, 1 skipped** (189 Dependency-Deprecation-Warnings); der Skip betrifft den ausschließlich auf Python 3.15 zielenden Lazy-Import-Smoke. Im normalen Projekt-`.venv` mit Python 3.15.2 liefen **263 Tests durch** (176 Deprecation-Warnings). `ruff check src tests` meldete **All checks passed**. Der echte `ProjectExecutionService` führte pytest und Ruff jeweils mit Exitcode 0 aus und erzeugte 27 begrenzte Prozessereignisse. Die frühere Live-Verifikation belegt Schema-Validierung, nicht die fachliche Qualität der Qwen-Antwort; deren Begründung paraphrasierte den Auftrag.

Weiterhin nicht implementiert sind allgemeine Toolaufrufe, RAG, LangGraph/Checkpointing und eine vollständige, workspace-weite Evidence-Kette. Nach echtem pytest-Fehlschlag läuft die UI im selben persistenten Run iterativ weiter, bis pytest besteht, der Nutzer abbricht, Modell-/Registry-/Root-/Interpreter-/Datei-Evidence wechselt, kein gültiger sicherer Patch verfügbar ist oder wiederholt derselbe redigierte Fehler bzw. bereits angewendete Dateiinhalt erscheint. Es gibt keine normale Drei-Versuche-Grenze. Jeder Einzeldatei-Diff bleibt sichtbar und benötigt eine eigene Apply-Freigabe; danach startet ausschließlich der passende manifestgebundene pytest-Retest automatisch und ohne zweite Ausführungsfreigabe. Run-, Step-, Patch-, Konsolen- und Testergebnis-Events teilen Run-ID, Projektwurzel/Fingerprint und die verwendete MIRO-Registry-Evidence. Testcode kann selbst Projektdateien ändern. Ein echter UI-SSE-Chat und ein manifestgebundener PySide6-Debugstart mit app-eigenem Stop wurden inzwischen live geprüft. Der 3.14-Pfad ist lokal verifiziert, aber eine Plattform-Sandbox oder allgemeine Prozesssicherheitsgrenze ist damit nicht belegt. Python 3.15 benötigt einen nachweislich kompatiblen Qt-/LangSmith-Paketpfad; es wurden hierfür keine Pakete installiert oder global verändert.
